## 1. 미션

각 단계의 부분 인식을 **하나의 정직한 악보**로 조립한다. 이론 규칙으로 음높이와 길이를 계산하고, 마디와 성부를 재구성하고, 코드와 가사를 붙이고, 반복 구조를 세운다. 모든 요소에 근거 박스와 보정된 신뢰도를 달고, 불확실한 곳에는 대안이 담긴 검토 힌트를 낸다. MusicXML이 HarmonyMaker에서 **그대로 열리게** 만든다.

이 역할은 **하드코딩 유혹이 가장 큰 자리**다. 특정 마디의 문제를 규칙으로 막고 싶어질 때마다 헌장 5절(실패 패턴 일반화)을 따른다.

v1.1(CPU 전용)에서는 네 역할이 더 무거워졌다. W6의 분류기는 작아서 국소적으로 애매한 판단을 **확률 후보로** 넘긴다. 그 후보 가운데 음악적으로 일관된 조합을 고르는 전역 제약 해석이 대형 모델이 하던 "문맥 읽기"를 대신한다. 네 규칙도 모두 규칙 카탈로그(`configs/assemble/rules.yaml`)에 등록한다(헌장 4.2절). 학습은 신뢰도 보정기(scikit-learn, 수 분)뿐이다.

## 2. 범위

- 범위: S5(이론 모듈, 마디·성부, 제약 해석, 근거 정렬, 텍스트 부착), S6(구조·진행), S7(보정, 힌트), S8(출력 전체), 파이프라인 통합, HarmonyMaker 호환 검사기
- 범위 밖: 인식 모델(W5–W7), 평가 지표(W4), HTTP(W9)

## 3. 작업 목록

### T8.1 이론 모듈 (CONTRACTS.md 5절)

- LSTL 항목 + 음자리표, 조표 문맥 → `Event`. 보표 위치 → 음이름, 변화표 결정 순서(보이는 임시표 → 붙임줄 → 마디 안 상태 → 조표), 길이(점, 셋잇단, 꾸밈음 0), 화음, 성부 시간축, 온마디 쉼표, 여러 마디 쉼표, 리듬 슬래시(pitch 없음)
- 음자리표 11종, 조표 ±7, 모든 길이 조합에 대한 전수 단위 시험과 hypothesis 속성 시험

### T8.2 오라클 경로 시험 — **가장 먼저 만든다**

- W2 라벨(정답 LSTL, 정답 기하, 정답 텍스트)을 **인식 결과 대신** 넣어 전체 조립과 출력을 돌린다. W4 평가기로 원본 MusicXML과 비교한다.
- 인식이 완벽하면 출력도 완벽해야 한다. 오차가 있으면 W8이나 W2 라벨의 결함이다. 이 시험이 조립 로직의 정확성을 모델과 분리해서 보증한다.
- CI 정규 시험으로 등록한다(SYN-Val 깨끗한 판본 일부).

### T8.3 마디 재구성

- W6 lattice의 `bar` 항목과 W5 barline을 `spanU`로 대응시켜 보표별 마디를 나눈다. system 안에서 보표 간 마디 경계를 맞춘다.
- barline이 빠졌거나 남으면 대안을 만들고 `BARLINE_UNCERTAIN` 힌트를 단다.
- 못갖춘마디 판정, 표시용 마디 번호, 시스템·페이지를 넘는 연속성(음자리표·조표 유지, 넘어가는 붙임줄)
- 파트 구성: brace로 묶인 보표 무리는 한 파트의 여러 보표, 나머지는 보표마다 파트다(CONTRACTS.md 3.7절). 시스템마다 보표 수가 다르면 세로 순서와 음자리표로 대응시키고 진단을 남긴다.

### T8.4 제약 해석 (ADR-017)

- 마디·성부마다 lattice의 대안(속성 상위 3개, N-best 가설)에서 조합을 골라 길이를 용량에 맞춘다. 점수는 분류기 로그확률 + 후보 생성기 간 일치도(+ 선택: test-time augmentation 일치도)다. 정확한 DP나 beam으로 풀고 결정적으로 동점을 깬다.
- (선택) **리듬 통계 사전**: 학습 코퍼스의 박자별 리듬 n-gram 빈도를 세어(학습이 아니라 계수, CPU 수 분) 점수에 작은 가중치로 더한다. 이 사전은 **시각적으로 지지되는 대안 사이의 순위만** 바꿀 수 있다. 채택은 ablation으로 정한다.
- **정직성 규칙(CONTRACTS.md 5.5절)**: 음표 삽입, 삭제, 채움 쉼표 생성은 금지다. 확신 ≥ 레지스트리 임계값(기본 9500 bp)인 속성은 뒤집지 않는다. 풀 수 없으면 `flagged` 또는 `blocked`로 두고 `DURATION_MISMATCH` 힌트에 후보를 담는다.
- v0는 보표마다 최선 가설 하나를 쓴다. v1은 barline에서 맞물리는 범위 안에서 **마디 단위로 N-best를 재조합**한다(ablation으로 채택).
- 보고: 제약 해석 전후 overfull 마디 수, 바뀐 속성 수, 바뀐 속성의 정답률(Dev-Tune).

### T8.5 근거 변환과 누락 신호

- lattice 항목마다 W6이 붙인 **근거 기호 ID**가 있다. 그 기호 박스를 W1 코어로 `original` 프레임에 옮겨 `symbol` 근거를 만든다. 마디 박스는 `measure` 근거로 만든다.
- 누락·과잉 신호: 읽기에 쓰이지 않은 높은 점수의 후보(누락 의심), 생성기 한 곳에서만 나온 약한 후보로 만든 음표(과잉 의심), 생성기 간 속성 불일치. **누락 의심은 음표를 넣지 않고** 마디에 `EVIDENCE_MISSING` 또는 `MODEL_DISAGREEMENT` 힌트를 단다.

### T8.6 텍스트 부착

- **코드 → onset**: 보표 안 이벤트 x 앵커로 x→시간 조각 선형 대응을 만든다. 코드 x 앵커를 가장 가까운 이벤트 onset에 붙이고(허용 거리는 staff-space 단위, 레지스트리), 이벤트가 없는 곳(긴 음표나 쉼표 위)은 박자 격자로 보간한다. 모호하면 `CHORD_POSITION_UNCERTAIN`.
- **가사 → 음표**: 절마다 음절 x 중심과 notehead x 중심을 **단조 DP**로 정렬한다. 멜리스마, 붙임줄 끝음, 쉼표 건너뛰기에 비용을 둔다. 모호하면 `LYRIC_ALIGNMENT_UNCERTAIN`.
- **방향 지시**: 템포, 섹션 라벨, 리허설 마크, 진행 문구를 가장 가까운 마디의 위치에 둔다(관례를 staff-space 규칙으로 표현).
- 제목과 부제를 `meta`로 옮긴다.

### T8.7 구조·진행 (S6)

- 도돌이 barline, 볼타(LSTL `ending` + W7 번호 텍스트), segno·coda 기호(LSTL), 진행 문구(W7) → `flow`
- 검증: To Coda가 있으면 Coda가 있어야 하고, D.S.가 있으면 Segno가 있어야 하고, 볼타 번호가 연속이어야 한다. 실패하면 `FLOW_UNRESOLVED`.
- 펼친 연주 순서를 계산한다(검증과 평가에 사용).

### T8.8 신뢰도 보정 (S7, ADR-006)

- 요소별 특징: 분류기 확률, 1–2위 차이, N-best 일치, 후보 생성기 간 일치, test-time augmentation 일치(있다면), 제약 해석으로 바뀌었는지 여부, 기하 신뢰도, 품질 지표
- 요소 유형별(event, harmony, lyric, measure, 조표·박자·음자리표, flow) 보정기: isotonic, Platt, temperature 중에서 고른다. **Dev-Tune과 SYN-calib에서만 적합**하고 Dev-Check로 검증한다.
- 요소 유형별 검토 임계값: Dev-Tune에서 K2 목표를 만족하면서 flag 부담이 가장 작은 운영점을 고른다. → 임계값 artifact 초안(EVALUATION.md 7.2절)
- `element-confidence.json` 생성

### T8.9 검토 힌트 (CONTRACTS.md 3.8절)

- 대안 출처: 속성 상위 후보, N-best, 제약 해석 후보, 코드 대안, 가사 대안
- 심각도: pitch, duration, 조표, 박자, 코드, 마디 구조는 `blocking`. 가사, 이음줄, 꾸밈음은 `warning`. 소비자 어휘 밖 코드와 곡 중간 템포 변경 같은 정보는 `info`.
- `labelKo`는 짧은 한국어("16분음표로 변경", "♭ 추가" 등). ID와 정렬은 결정적이어야 한다.

### T8.10 출력기 (CONTRACTS.md 8절)

- MusicXML 작성기(8.2절 프로필), MusicXML 4.0 XSD 검증, **재파싱 동등성 시험**. 재파싱용 최소 판독기는 엔진 안에 따로 둔다. W4 평가기와는 독립 구현이며, 두 구현이 서로를 교차 검증한다.
- `evidence.json`, `review-hints.json`, `element-confidence.json`, `report.json`, `runtime.json` 작성기
- 상태 결정(complete, partial, blocked)과 오류 코드, `partial.musicxml`, rejected-output 번들 조립 함수(W9가 HTTP에서 사용)

### T8.11 HarmonyMaker 호환 검사기

CONTRACTS.md 8.2절과 12절에 적힌 HarmonyMaker 가져오기 제약(overfull, 음수 backup, 0 길이, 앞 음 없는 chord, 리듬 슬래시 표현, 가사 syllabic/extend, harmony 구조)을 Python으로 재구현해 **모든 complete 출력에 CI로 적용**한다. 최종 판정은 G4의 HarmonyMaker E2E다.

### T8.12 파이프라인 통합

- W1의 mock 단계를 실제 단계로 하나씩 교체한다. 단계별 설정, 오류 전파, 부분 실패 처리(한 보표 실패가 전체를 막지 않게 하고 해당 마디를 blocked로 둔다)
- 통합 시험: SYN-Val 일부와 R-Dev 전체. 단계별 지연과 메모리를 `runtime.json`에 기록한다.

## 6. 이 역할의 함정

- **마디 하나를 위한 규칙**: "이 경우엔 점을 지운다" 같은 규칙을 넣고 싶다면, 그것은 대개 제약 해석의 점수나 대안 공급 문제다. 일반 규칙으로 바꿀 수 없으면 넣지 않는다.
- **보이지 않는 음표로 박자 채우기**는 절대 금지다(F9). 박자가 안 맞는 것은 정직하게 flag한다. 그것이 HarmonyMaker가 원하는 동작이다.
- **보정의 데이터 누수**: 보정기와 임계값을 Dev-Check나 sealed로 적합하지 않는다.
- 힌트를 과도하게 달면 K2는 좋아지지만 사용자는 지친다. flag 부담을 항상 함께 보고한다.
